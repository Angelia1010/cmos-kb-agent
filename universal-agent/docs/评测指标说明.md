# KB-Agent 评测指标与结果口径说明

本文对应 [`scripts/eval_kbagent.py`](../scripts/eval_kbagent.py) 的**当前实现**，用于解释命令、输入输出、指标公式、有效样本和异常处理。它是口径说明，不包含某一次运行的指标结论。不同批次比较前，应先确认测试集、响应文件、judge 模型、`--doc-chars` 和通过阈值相同。

## 1. 评测流程与数据

脚本有三个子命令：

| 阶段 | 输入 | 动作 | 主要输出 |
| --- | --- | --- | --- |
| `collect` | `.xlsx` / `.xlsm` / `.json` 测试集 | 调用 KB-Agent 服务，采集每条问题的完整响应 | `responses.jsonl` |
| `judge` | `responses.jsonl`；可选原测试集补 gold | 用 LLM 分别评审检索结果和坐席话术，再汇总 | `verdicts.jsonl`、报表文件 |
| `report` | `verdicts.jsonl` | 不调用 LLM，按指定话术阈值重新汇总 | 报表文件 |

`collect` 读取测试集后，同一“省份＋问题”的 Excel 行会合并为一个案例；`--province`、`--offset`、`--limit` 和 `--sample-seed` 会改变本次案例集合。案例数是实际处理的案例数，不一定等于 Excel 数据行数。

一个 `responses.jsonl` 记录至少需要 `case_id`、`query` 和 KB-Agent 的 `object`；若要计算 gold 指标，还需 `gold_ids`、`gold_titles` 或 `gold_atoms`。`judge --testset` 可按 **query 完全相同** 的文本补齐缺失的 gold；它不会模糊匹配问题。可直接评已有响应文件，无需再次 `collect`。

评测读取 `object.sources` 的**前 3 篇**作为排序后的 Top3，读取 `object.retrievedDocs` 作为重排前召回列表。LLM 评审每篇文档时看到标题及正文前 `--doc-chars` 个字符，默认 3000；它并非查看网页展示的“最相关片段”。检索与话术各进行一次独立 judge 调用；调用或结果校验失败时，每项立即重试 1 次。

> 本脚本没有单独的 `rank` 子命令。若使用其他排序脚本，其结果应先整理为 `responses.jsonl`，再运行 `judge`。

## 2. 有效样本与分母

**`total_cases` 是 `verdicts.jsonl` 的记录行数**。下列集合决定各指标的分母，不应把“案例总数”直接当作所有百分比的分母。

| 集合 / 计数 | 当前实现 | 用途 |
| --- | --- | --- |
| `service_errors` | `service_error` 或 `fatal_error` 非空的记录数 | 表示采集响应失败、`object` 为空或单案例评审发生未捕获错误；这些记录不进入 A/B 指标 |
| `judged` | 总记录去掉上述服务错误 | 客观字符串指标、降级计数的基础集合 |
| A 有效样本 | `judged` 中没有 `retrieval.judge_error` 的记录 | A0、A2、A3、A4 的基础集合；**Top3 为空且无 judge 错误仍计入**，该案例的命中率、Precision、RR 均为 0 |
| A1 有效样本 | A 有效样本中 `retrieval.gold_hit` 非 `null` 的记录 | A1 的实际分母；需有至少一种 gold 标注 |
| A5 / 参考 Top3 字符串匹配有效样本 | `judged` 中相应 `objective.*_gold_hit` 非 `null` 的记录 | 两项可有不同分母；A5 还要求 `retrievedDocs` 非空 |
| B 有效样本 | `judged` 中没有 `answer.judge_error`，且 `answer` 中没有 `note` 的记录 | 通过率、各维度均分等的基础集合；话术和办理建议都为空时有 `note=话术为空`，不计入 |
| B6 有效样本 | B 有效样本中 judge 与系统的可用性等级都非空的记录 | B6 的实际分母，另以 `B6_样本数` 输出 |

单个案例的检索 judge 可能成功、话术 judge 失败，或相反。因此 A、B 可以使用不同的样本集合。`judge_errors.retrieval` 与 `judge_errors.answer` 分别计数，同一案例可能同时出现在两项中，**不能相加当作出错案例数**。缺值被 `_rate` 排除；没有有效样本时结果为 `null`，控制台显示 `N/A`，不是 0%。

## 3. A 类：检索质量

LLM 对每篇 Top3 文档独立输出：

- `gold_match`：`yes/no`，判断文档是否与 gold 指向同一知识或业务。
- `query_relevant`：`yes/partial/no`，分别表示能回答核心问题、仅主题相关、无有效关联。

### 3.1 文档级判定规则

这两个标签回答的是**不同问题**：`gold_match` 判断“是不是标准答案对应的知识”，`query_relevant` 判断“这篇文档能不能回答用户当前问的点”。judge 结合**标题和截断后的正文**逐篇判断，不能把标题相似直接等同于“能回答问题”。

| 标签 | 判定为肯定的条件 | 判定为否定的条件 |
| --- | --- | --- |
| `gold_match=yes` | 与任一 gold 标题/原子名称指向同一知识或同一业务；允许同义改写、标点和前后缀差异，正文能确认属于同一知识也可以 | — |
| `gold_match=no` | — | 与所有 gold 都不是同一知识；只是同类业务、相关背景或周边产品也不算。标准答案为“(无)”时，提示词要求一律输出 `no` |

`query_relevant` 的三档边界如下：

| 标签 | 实际含义 | 例子：用户问“新版欢孝流量安心包有年龄限制吗？” |
| --- | --- | --- |
| `yes` | 文档给出能回答**全部或核心部分**的明确依据，包括关键条件、结论或办理规则；不要求覆盖用户未问的资费等信息 | 文档写明“仅限 65 岁及以上客户办理，截至当年 1 月 1 日满 65 周岁” |
| `partial` | 与同一产品/问题主题有关，可提供背景，但**缺少回答所问关键点的依据**；凭此文档不能直接给用户结论 | 只写该包月费、流量额度和有效期，没有年龄条件 |
| `no` | 与问题无关，或只是其他产品/业务，不能为当前回答提供有效信息 | 另一款无关流量包的办理规则 |

因此，**同一篇文档可以 `gold_match=yes`、`query_relevant=partial`**：它确实是 gold 对应的产品文档，但展示给 judge 的正文只有资费，缺少用户所问的年龄条件。反过来，非 gold 文档若确实有可用的同类通用规则，也可能被 judge 判为与问题相关；两个标签不会相互推导。

这些是传给 LLM 的提示词判定标准，不是脚本中的关键词匹配或硬编码规则。边界案例可能随模型输出波动；应查看 `eval_details.xlsx` 的 D1～D3 标签和理由，并到 `responses.jsonl` 核对对应文档的送评正文。尤其要注意正文按 `--doc-chars` 从开头截断，完整原文有答案但送评片段没有时，judge 仍可能给 `partial`。

### 3.2 从文档标签到案例指标

一条案例的 Top3 最多 3 篇；不足 3 篇时只评实际返回的文档，但 A3 的除数仍是 3。

**先按案例判命中，再按案例汇总：**A0、A1、A2、A2~ 的单案例结果都是布尔值。Top3 有 1 篇满足条件与有 3 篇满足条件，这条案例都只记 **1 次命中**；0 篇满足条件才记未命中。最终的百分比是“命中案例数 ÷ 有效案例数”，**不是“命中文档数 ÷ Top3 文档数”**。例如 100 条有效问题中有 80 条各找到至少一篇符合条件的文档，命中率就是 80%，无须每条再除以 3。

这里的“符合条件”有不同口径：**A0 综合命中**要求 Top3 任一篇 `gold_match=yes` **或** `query_relevant=yes`；两种条件可以由不同文档满足。A1 单独要求至少一篇与 gold 指向**同一知识**；A2 单独要求至少一篇能回答问题的全部或核心部分；A2~ 还把仅主题相关、但**不足以回答问题**的 `partial` 算入。**A0 不把 `partial` 作为命中**，因为它不能回答用户问题。

| 指标（`eval_summary.json` 字段） | 案例计算方式 | 汇总方式 / 分母 |
| --- | --- | --- |
| **A0 Top3 综合命中率**（`A0_top3综合命中率...`） | Top3 任一篇 `gold_match=yes` 或 `query_relevant=yes` 则命中 | 命中案例数 ÷ A 有效样本数；无 gold 时仍可凭问题相关性命中 |
| **A1 Top3 准确率**（`A1_top3准确率...`） | 有至少一篇 `gold_match=yes` 则命中 | 命中案例数 ÷ A1 有效样本数；无 gold 为 `null`，不进入分母 |
| **A2 问题相关率**（`A2_问题相关率...`） | 有至少一篇 `query_relevant=yes` 则相关 | 相关案例数 ÷ A 有效样本数 |
| **A2~ 宽松相关率**（`A2_loose(含partial)`） | 有至少一篇 `yes` 或 `partial` 则相关 | 宽松相关案例数 ÷ A 有效样本数 |
| **A3 Precision@3**（`A3_precision@3`） | `(yes 篇数 + 0.5 × partial 篇数) / 3` | 案例分数的算术均值，范围 0～1；不足 3 篇的空位相当于 0 |
| **A4 MRR@3**（`A4_mrr@3`） | 第一篇 `yes` 的排名为 `r`，得 `1/r`；没有 `yes` 得 0 | 案例 RR 的算术均值；`partial` 不算命中 |
| **A5 召回命中率**（`A5_召回命中率...`） | gold ID/标题与 `retrievedDocs` 中任一 ID/标题字符串匹配 | 命中案例数 ÷ 有 gold 且 `retrievedDocs` 非空的非服务错误案例数 |
| **参考 Top3 字符串匹配率**（`参考_top3字符串匹配率...`） | gold ID/标题与 `sources[:3]` 中任一 ID/标题字符串匹配 | 命中案例数 ÷ 有 gold 的非服务错误案例数；不调用 LLM |
| **召回命中但 Top3 丢失** | `recall_gold_hit is True` 且 `top3_gold_hit is False` | **案例数**，不是百分比；两边均为字符串匹配口径 |

A5 和参考 Top3 字符串匹配调用同一 `gold_hit` 函数：ID 去空白、转小写后全等；两边均至少 8 字符时还允许前缀互含，以容忍截断 ID。标题去空白、转小写并删除部分标点后，允许全等或互相包含。**A1 是 LLM 语义判定，A5/参考 Top3 是字符串判定，不能直接用差值推断重排效果。**

示例：Top3 相关性依次为 `partial / yes / no`，则本案例 A0=命中、A2=命中、A2~=命中、A3=`(0.5+1+0)/3=0.5`、A4=`1/2=0.5`。若仅返回 1 篇且为 `yes`，A3 仍是 `1/3`，A4 为 1。若 Top3 的 gold 均为 `no`、问题相关性均为 `partial`，A0=未命中，但 A2~=命中。

**数据边界：**

- `retrievedDocs` 缺失或为空时，A5 记 `null`，不算“召回未命中”；有召回列表但未匹配到 gold 才记 `False`。
- A1 的请求把 gold **标题和原子名称**提供给 LLM，未把 gold ID 放进提示词。若样本只有 `gold_ids`，代码仍将它视为“有 gold”而计入 A1，但模型看到的标准答案是“(无)”，提示词要求输出 `gold_match=no`。这类样本的 A1 不宜用来衡量真实命中率，应先补标题/原子标注。
- `gold_atoms` 会进入 A1 的 LLM 提示词，但**不会**用于 A5 或参考 Top3 字符串匹配；仅有原子、没有 ID/标题时，后两项为 `null`。
- A5 与参考 Top3 字符串匹配的分母可能不同；此外 `retrievedDocs` 与 `sources` 的字段、数据范围可能不一致。看到“A5 低于 Top3 字符串匹配率”时，应先核查两份原始列表和有效样本，而不能直接认定重排有问题。

## 4. B 类：坐席话术质量

话术 judge 读取用户问题、`object.script`、`object.handlingSuggestion` 与 Top3 文档标题及截断正文，对 B1～B5 各给 0/1/2 分：

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| B1 `b1_relevance` 回答相关性 | 直接完整回应问题 | 部分回应或避重就轻 | 答非所问 |
| B2 `b2_faithfulness` 忠实性 | 所有事实陈述有参考依据 | 大部分有依据，个别找不到来源 | 多处无依据编造 |
| B3 `b3_consistency` 一致性 | 与参考文档无矛盾 | 别表述不个精确，无实质矛盾 | 与参考文档直接矛盾 |
| B4 `b4_completeness` 完整性 | 覆盖问题全部关键点 | 遗漏次要关键点 | 遗漏核心关键点 |
| B5 `b5_usability` 坐席可用性 | 可直接照读，无内部术语泄漏 | 基本可用，需小改 | 无法直接照读 |

这五项是**分别打分**，不能互相替代。B1 看有没有回应用户问题；B2 看事实陈述是否有送评文档支持；B3 看有没有与文档直接冲突；B4 看用户所问关键点是否覆盖；B5 看坐席能否照读。例如“月费 10 元”在送评文档中找不到依据，属于 B2 的无依据问题；若文档明确写“月费 20 元”，还涉及 B3 的直接矛盾。遗漏年龄门槛首先影响 B4；写出内部知识 ID 首先影响 B5。各维 0/1/2 的具体取值仍由 LLM 按上表提示词判断，脚本只校验分值并计算汇总。

| 汇总指标 | 计算方式 |
| --- | --- |
| **话术通过率** | B1≥`--pass-b1-min` 且 B2≥`--pass-b2-min` 且 B3≥`--pass-b3-min` 的案例数 ÷ B 有效样本数。**当前默认是 B1≥1、B2≥1、B3≥1**；B4/B5 不参与通过判定 |
| **参考严格通过率** | 固定按 B1≥1、B2≥1、B3≥2 计算，不受当前命令的阈值参数影响 |
| **B1～B5 均分** | 各维度有效分数的算术均值，范围 0～2；分母可能因历史 `verdicts` 缺字段而不同 |
| **B3 致命矛盾率** | `b3_consistency=0` 的案例数 ÷ 含 B3 分数的 B 有效样本数；B3=1 不属于“致命矛盾” |
| **B6 自评一致率** | `answer.judge_usability == system_usability` 的案例数 ÷ 两者都非空的 B 有效样本数；这是等级**完全相等**比例，不是与人工标注比较的准确率 |

可用性等级是 `directly_usable`、`verify_first`、`not_usable`。系统等级来自响应的 `object.usability.level`。两者都缺或其中一个缺时，B6 不计入；`B6_样本数=0` 时结果为 `null`。

**特别注意：**只要 `script` 或 `handlingSuggestion` 至少有一个非空，代码就会调用话术 judge；即便 `script` 为空而办理建议非空，也可能得到 B 分数。因此“B 有效样本”不等同于“话术文本非空样本”。`--doc-chars` 截断到正文前部，若答案依据落在截断之后，B2/B3 的判断可能受影响。更改 `--doc-chars` 需要重跑 `judge`；仅运行 `report` 不会重新判分。

## 5. 错误、降级与 badcase

| 输出项 | 解释 |
| --- | --- |
| `service_errors` | 采集出错、空响应或单案例致命错误；不进 A/B 统计 |
| `judge_errors.retrieval` / `judge_errors.answer` | 相应 judge 两次尝试后仍失败的案例数；仅从对应指标分母排除，不代表质量不通过 |
| `degraded_count` | 非服务错误记录里 `object.degraded` 为真的案例数；**降级案例仍可进入 A/B 指标** |
| `badcases.csv` | 满足任一失败筛查条件的案例列表，既可能是质量问题，也可能只是服务/judge 错误、降级或 Top3 字符串未匹配 gold |

脚本用逐条落盘实现断点续跑：`collect` 遇到已有 `case_id` 的 `responses.jsonl` 会跳过；`judge` 遇到已有 `case_id` 的 `verdicts.jsonl` 也会跳过，**包括曾经 judge 超时的案例**。`report` 不补评错误样本。因此重跑同一个 `--out` 不会自动修复超时记录；需单独筛出失败案例补评，并避免合并时同一 `case_id` 重复。若 `verdicts.jsonl` 存在重复 ID，`report` 按每一行统计，并不去重。

`badcases.csv` 的行数不等于“话术不通过数”：其规则还包括检索未命中、检索不相关、字符串未匹配、重排丢失、降级、空话术及各类错误。它是人工排查清单，不能直接用作通过率分子或分母。

## 6. 输出文件与建议的阅读顺序

| 文件 | 内容 |
| --- | --- |
| `responses.jsonl` | 每案例采集到的响应及 `error`、采集耗时；`collect` 生成 |
| `verdicts.jsonl` | 逐案例的客观匹配、LLM 判定、话术分数及错误；`judge` 生成 |
| `eval_summary.json` | 总数、错误数、A/B 指标；`judge` 或 `report` 生成 |
| `eval_details.xlsx` | “明细”和“汇总”工作表，供筛选具体案例；`judge` 或 `report` 生成 |
| `badcases.csv` | 带失败原因的排查清单，UTF-8 BOM 编码，便于 Excel 打开 |

建议先看 `service_errors`、`judge_errors` 与 A/B 有效样本数，确认缺失比例；再看核心指标；最后在 `eval_details.xlsx` 核查对应案例的原文、分数和 judge 理由。指标升降只有在**相同案例集合与相同判定条件**下才可直接比较。

当前 `verdicts.jsonl` 的 `retrieval.top3_hit` 是 A0 的逐案例结果；`gold_hit` 与 `any_yes` 仍分别保留。旧版 verdict 没有 `top3_hit` 时，`report` 会用已保存的 `gold_hit is True or any_yes is True` 重算 A0，无需重新调用大模型。控制台日志中的“综合命中”对应 A0，“gold命中”和“问题相关”分别对应 A1、A2 的单案例判断。

## 7. 命令示例（PowerShell）

在 `universal-agent` 目录运行，替换示例路径与服务地址：

```powershell
python scripts/eval_kbagent.py collect `
  --testset 'D:\cmos\Agent-知识库\测试评估\知识库检索样本合集.xlsx' `
  --kbagent-url 'http://<KB服务地址>/api/kb-agent-service/prod/retrieve' `
  --out 'eval_run1' --workers 2 --limit 320

python scripts/eval_kbagent.py judge `
  --responses 'eval_run1/responses.jsonl' `
  --llm-url 'http://<LLM服务地址>:8002/llm_397b_api' `
  --out 'eval_run1' --workers 2 --doc-chars 3000

# 只调整通过门槛并重新出报表，不重新请求 judge：
python scripts/eval_kbagent.py report `
  --verdicts 'eval_run1/verdicts.jsonl' `
  --out 'eval_run1' --pass-b3-min 2
```

`--workers` 默认 2；`--kb-timeout` 默认 600 秒，`--llm-timeout` 默认 300 秒，分别是客户端请求等待时间。服务返回超时码或 502 时，增大客户端等待时间本身不保证成功。上例的 `--limit 320` 只影响 `collect` 阶段；`judge` 会处理 `responses.jsonl` 中的全部未评案例。

## 8. 跨批次比较检查

比较两轮报告时，至少记录：测试集文件及抽样方式、实际 `case_id` 集合、`responses.jsonl` 内容、服务与 judge 模型版本、`--doc-chars`、B1/B2/B3 阈值、服务错误数、两类 judge 错误数以及各指标有效样本数。相同话术和材料若 judge 模型输出不同，B 分数仍可能变化；若超时样本不同，分母也会变化。只有阈值变化时，可用 `report` 在同一份 `verdicts.jsonl` 上重算，隔离判定门槛造成的差异。

## 9. 实际发送给大模型的 judge 提示词

以下是脚本中 `RETRIEVAL_JUDGE_PROMPT` 和 `ANSWER_JUDGE_PROMPT` 的**运行时文本模板**。调用前会替换花括号占位符；下方 JSON 示例使用模型实际看到的单层 `{`、`}`，Python 源码里为了 `.format(...)` 将这些字面花括号写成了双层 `{{`、`}}`。除案例数据替换外，提示词没有额外的 system 消息：`call_llm` 将完整提示作为 `{"query": prompt}` 发给 `--llm-url`。

### 9.1 检索 judge（`RETRIEVAL_JUDGE_PROMPT`）

```text
你是10086客服知识库的检索评测专家。给定用户问题、标准答案(gold:知识标题/原子名称)、以及检索系统返回的Top3文档(标题+正文摘录),请对每篇文档独立做两个判定。

[判定1 gold_match — 是否命中标准答案]
结合文档标题和正文,判断该文档与"标准答案"中的任一条是否指向同一个知识/业务:
- yes: 就是标准答案对应的知识。标题语义一致即可(同义改写/简繁/标点/前后缀差异都算命中),或正文内容表明其与标准答案是同一业务知识点。不要求字符串完全一致
- no: 与所有标准答案都不是同一知识,或只是相关背景/周边业务
(标准答案标注为"(无)"时,gold_match 一律输出 "no")

[判定2 query_relevant — 是否与用户问题相关]
结合文档标题和正文:
- yes: 该文档能回答用户问题的全部或核心部分
- partial: 主题相关,但不足以回答问题(只有背景/周边信息)
- no: 与问题无关,无法为回答提供有效信息

[用户问题]
{query}

[标准答案]
{golds}

[候选文档]
{docs}

[输出要求]
只输出一个JSON对象,不要任何解释文字,不要markdown代码块标记,格式:
{"judgments":[{"doc":"D1","gold_match":"yes","query_relevant":"yes","reason":"一句话理由"}]}
judgments 必须按顺序包含全部候选文档。
```

### 9.2 话术 judge（`ANSWER_JUDGE_PROMPT`）

```text
你是10086客服话术质量评测专家。给定用户问题、系统检索到的参考文档、以及系统生成的坐席话术,请按以下5个维度独立打分(每维0/1/2分)。

[评分维度]
b1_relevance 回答相关性: 2=直接完整回应用户问题 1=部分回应或避重就轻 0=答非所问
b2_faithfulness 忠实性: 2=话术中所有事实陈述(数字/条件/时间/流程)都能在参考文档中找到依据 1=大部分有依据但个别陈述找不到来源 0=存在多处无依据的编造
b3_consistency 一致性: 2=与参考文档无任何矛盾 1=个别表述不精确但无实质矛盾 0=存在与参考文档直接矛盾的陈述
b4_completeness 完整性: 2=覆盖用户问题的全部关键点 1=遗漏了次要关键点 0=遗漏了核心关键点
b5_usability 坐席可用性: 2=口语化、可直接照读给用户、无内部术语或文档ID泄漏 1=基本可用但需小幅修改 0=无法直接照读

另给出综合可用性判定 judge_usability,三选一:
- directly_usable: 可直接照读
- verify_first: 需人工核实后使用
- not_usable: 不可用

[用户问题]
{query}

[坐席话术]
{script}

[办理建议]
{suggestion}

[参考文档]
{docs}

[输出要求]
只输出一个JSON对象,不要任何解释文字,不要markdown代码块标记,格式:
{"b1_relevance":2,"b2_faithfulness":2,"b3_consistency":2,"b4_completeness":2,"b5_usability":2,"contradictions":["与原文矛盾的陈述,无则空数组"],"uncovered":["遗漏的关键点,无则空数组"],"reasons":{"b1":"一句话","b2":"一句话","b3":"一句话","b4":"一句话","b5":"一句话"},"judge_usability":"directly_usable"}
```

### 9.3 占位符、正文截断与重试

| 占位符 | 实际填入的内容 |
| --- | --- |
| `{query}` | 当前案例的 `query` |
| `{golds}` | 每个 `gold_titles` 独占一行、前缀 `- `；若有 `gold_atoms`，追加 `(涉及知识原子: 原子1、原子2)`；两者都没有时为 `(无)`。**`gold_ids` 不进入提示词** |
| `{docs}` | `sources[:3]` 按序组成 `<D1> 标题: ...\n正文: ...\n</D1>` 等文档块，块之间空一行；正文取 `content` 的前 `--doc-chars` 个字符，超长时追加 `…(截断,原文N字)`；无文档时为 `(无检索结果)` |
| `{script}` / `{suggestion}` | 分别是 `object.script` / `object.handlingSuggestion`；其中一项为空而另一项非空时，空项填 `(空)` |

只有存在 `sources` 才发送检索提示词；只有话术或办理建议至少一项非空才发送话术提示词。任何调用异常或输出解析、字段校验失败，`_judge_with_retry` 都会再试一次，并在**原提示词末尾**追加以下文字：

```text
[注意]你上一次的输出无法解析。请严格只输出一个JSON对象,不要包含任何其他文字或代码块标记。
```

目前即使上次失败原因是超时或 HTTP 502，也会追加这句“输出无法解析”；它是脚本的实际行为，并不代表上次真的返回了不可解析内容。
