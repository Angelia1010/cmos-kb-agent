# KB-Agent 检索与话术评测指标说明

> 脚本:`scripts/eval_kbagent.py`(LLM-as-Judge)
> 本文档解释 `eval_summary.json` / 控制台报表中每个指标的含义、计算口径,并对一次约 300 条样本的实跑结果做诊断。

---

## 0. 总体设计

评测分两大块,逐案例打分后汇总:

- **A. 检索质量** —— 评 Top3 检索结果(`object.sources` 前 3 篇)好不好。
- **B. 话术质量** —— 评基于检索结果生成的坐席话术(`object.script`)好不好。

**案例级口径**:检索指标以"一个案例的 Top3 里只要有任一篇满足条件就算这个案例对",最后统计所有案例的命中比例(%)。文档级指标(Precision@3 / MRR@3)则考虑 Top3 内部排位。

评审方式是 **LLM-as-Judge**:把用户问题、标准答案(gold)、Top3 文档(标题+正文摘录)喂给生产大模型(`/llm_397b_api`),让它按固定标准逐篇输出判定,再程序化汇总。gold 匹配是**语义判断,不要求字符串完全一致**。

---

## 1. A. 检索质量指标

judge 对每篇 Top3 文档做**两个独立判定**:
- `gold_match`(yes/no):结合标题+正文,该文档是否与标准答案指向同一知识/业务。
- `query_relevant`(yes/partial/no):结合标题+正文,该文档是否能回答用户问题。

案例级再由这 3 篇的判定汇总而成。

| 指标 | 含义 | 计算方式 | 怎么读 |
|---|---|---|---|
| **A1 Top3准确率** | 检索"找对了知识"的比例(核心) | 案例的 3 篇里 **≥1 篇 `gold_match=yes`** → 该案例命中;命中数 / **有 gold 标注的案例数** | 越高越好。只统计有标准答案的样本 |
| **A2 问题相关率** | 检索"答得上问题"的比例(核心) | 3 篇里 **≥1 篇 `query_relevant=yes`** → 命中 | 越高越好。这是话术质量的上游天花板 |
| **A2~ 宽松相关** | 放宽到"沾边就算" | ≥1 篇 `yes` 或 `partial` | 与 A2 差距大 = 很多文档只是"周边相关"而非"直接能答" |
| **A3 Precision@3** | Top3 的平均"含金量" | 每篇 yes=1、partial=0.5、no=0,求和 / 3,再对案例取均值 | 满分 1.0。0.55 ≈ 平均每个案例 Top3 里约 1.6 篇是"直接相关" |
| **A4 MRR@3** | 第一篇答得上问题的文档排得多靠前 | 首个 `yes` 的排名倒数(第1名=1.0,第2=0.5,第3=0.33,无 yes=0),案例取均值 | 越接近 1 说明相关内容越靠前 |
| **A5 召回命中率** | gold 是否出现在**重排前的召回全集**(`retrievedDocs`) | gold 与召回列表做**字符串比对**,命中比例 | 用来区分"根本没捞到" vs "捞到了但被重排排掉" |
| **召回命中但Top3丢失(重排损耗)** | 召回里有、Top3 里没了的案例数 | `recall_gold_hit=True 且 top3_gold_hit=False` 的计数 | 数字大 = 重排环节把对的文档挤掉了 |
| **参考 Top3字符串匹配率** | 旧的严格口径(对照用) | gold ID/标题 与 Top3 做**字符串**完全/前缀/互含匹配 | 与 A1(LLM)对比,差值 = 语义匹配比字符串多认出的命中 |

### 本次结果解读(A)

| 指标 | 值 | 解读 |
|---|---|---|
| A1 Top3准确率 | **79.8%**(有gold 297) | 约 8 成案例 Top3 里找到了标准知识,2 成没找到 |
| A2 问题相关率 | **75.1%** | 3/4 案例至少有一篇能直接答问题——**这 25% 的缺口直接拖垮话术** |
| A2~ 宽松相关 | **97.0%** | 只有 3% 案例 Top3 完全无关,说明"完全跑偏"很少,多是"沾边但答不全" |
| A3 Precision@3 | **0.554** | Top3 有噪声:平均只有约 1.6 篇真正相关,不是 3 篇都干净 |
| A4 MRR@3 | **0.662** | 第一篇相关文档通常排在第 1~2 位,排位尚可 |
| A5 召回命中率 | **36.3%** | ⚠️ 见下方"数据质量警示"——这个值异常偏低,大概率不可信 |
| 重排损耗 | **34 例** | 有 34 个案例召回捞到了但没进 Top3,同样受 A5 数据问题影响,谨慎采信 |
| 参考 Top3字符串匹配率 | **65.0%** | 比 A1(LLM)低 14.8 个点,证明改用语义判断是对的:很多命中标题写法不同,字符串匹配会漏判 |

> **A5 数据质量警示**:逻辑上召回全集(Top100)是 Top3 的超集,所以 A5 召回命中率(字符串)**应当 ≥** 参考 Top3 字符串匹配率。但实测 36.3% < 65.0%,矛盾。原因几乎可以肯定是:你的 jsonl 由 Excel 转来,`retrievedDocs`(Top100 召回列表)列为空或标题写法与 Top3 不一致,导致 A5 及重排损耗统计失真。**A5 这一轮不要用来下结论**,需从完整链路重新导出召回明细再评。

## 2. B. 话术质量指标

judge 对话术按 **0/1/2** 三档打分(5 个维度),再给一个综合可用性判定。

| 维度 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| **B1 b1_relevance** 相关性 | 直接完整回应问题 | 部分回应/避重就轻 | 答非所问 |
| **B2 b2_faithfulness** 忠实性 | 所有事实(数字/条件/流程)都能在参考文档找到依据 | 大部分有依据,个别找不到来源 | 多处无依据编造(幻觉) |
| **B3 b3_consistency** 一致性 | 与参考文档无任何矛盾 | 个别表述不精确但无实质矛盾 | 有直接矛盾的陈述 |
| **B4 b4_completeness** 完整性 | 覆盖全部关键点 | 遗漏次要关键点 | 遗漏核心关键点 |
| **B5 b5_usability** 坐席可用性 | 口语化、可直接照读 | 基本可用需小改 | 无法照读 |

**汇总指标**:

| 指标 | 含义 | 计算方式 |
|---|---|---|
| **话术通过率** | 话术"能用"的比例(核心) | **B1≥1 且 B2≥1 且 B3=2** 三者同时满足才算通过。注意 B3 必须满分 2(零矛盾) |
| **B3 致命矛盾率** | 话术与原文直接打架的比例 | B3=0 的案例占比。**一票否决项** |
| **b1~b5 均分** | 各维度平均分(0~2) | 对所有有效案例取均值 |
| **B6 自评一致率** | 系统自评的可用性 vs judge 判的可用性是否一致 | 两者都非空时比对;样本 0 → N/A |

### 本次结果解读(B)

| 指标 | 值 | 解读 |
|---|---|---|
| 话术通过率 | **55.7%** | 只有约一半话术"可直接用" |
| b1_relevance | **1.934**/2 | 相关性很好——话术基本都对着问题答 |
| b2_faithfulness | **1.194**/2 | ⚠️ 偏低——不少话术含"文档里找不到依据"的陈述 |
| b3_consistency | **1.311**/2 | ⚠️ 偏低——通过线要求 B3=2,均分才 1.3,大量案例卡在 1 分 |
| b4_completeness | **1.370**/2 | 中等——常遗漏关键点 |
| b5_usability | **1.640**/2 | 尚可——口语化/可照读还行 |
| B3 致命矛盾率 | **25.6%** | ⚠️ 每 4 条就有 1 条与原文直接矛盾,是通过率低的主因之一 |
| B6 自评一致率 | **N/A**(样本0) | 系统 `usability.level` 没进 jsonl,无法校准(数据缺失,非质量问题) |

## 3. 为什么话术质量这么低?——根因诊断

话术通过率低(55.7%)**不是单一环节的问题,而是"上游检索天花板 + 严格通过线 + judge 口径"三者叠加**:

**① 上游检索限制了话术天花板(最主要)**
话术是"看着 Top3 文档写出来的"。A2 问题相关率只有 **75.1%**,意味着约 **1/4 的案例 Top3 里根本没有能直接回答问题的文档**。这种情况下生成模型只能:
- 硬编 → **B2 忠实性↓**(文档没依据)、**B3 一致性↓**(与原文矛盾);
- 或写得很泛 → **B4 完整性↓**。
所以 b2=1.194、b3=1.311、b4=1.370 这几个低分,很大程度上是检索没喂对料导致的,不是生成模块单独的问题。**要提话术,先提 A2。**

**② 通过线本身很严(设计如此)**
通过要求 **B3=2(零矛盾)**。b3 均分只有 1.311,说明大量案例是 B3=1(个别表述不精确)——这些**内容其实基本可用,但因为不是满分 2,一律判不通过**。再叠加 25.6% 的 B3=0 致命矛盾,通过率自然被压到 55.7%。这条严格线是刻意设的(见项目"话术一致性收紧"原则:宁可让坐席多核实,不放过矛盾),所以"通过率低"部分是**标准严**,不完全等于"话术差"。

**③ judge 只看到截断正文(可能低估 B2)**
评审时单篇文档正文默认截断到 3000 字(`--doc-chars`)。若话术引用了截断点之后的原文内容,judge 会判"找不到依据" → **B2 被低估**。原始知识较长时,这会系统性压低忠实性分。

**④ B6 无法校准(数据缺失)**
系统自评的 `usability.level` 没写进 Excel/jsonl,B6 样本=0。这不是质量差,是**数据没带全**,导致"系统自评 vs judge"这条交叉验证线失效。

**⑤ LLM judge 自身有噪声**
单模型单次评审、无多评投票,judge 对"矛盾/依据"的判断本身有波动,尤其 B2/B3 这种主观维度。个别低分可能是误判。

## 4. 下一步建议

**先定位、再改**:
1. **开 `badcases.csv` / `eval_details.xlsx`**,按失败原因筛:
   - `top3与问题不相关`(A2 失败)→ 检索问题,归到检索优化;
   - `b3_consistency=0`(25.6% 致命矛盾)→ 逐条看是真矛盾还是 judge 误判;
   - `b2_faithfulness=0` → 看是真幻觉还是"引用了截断外正文"。
2. **量化"检索拖累话术"的比例**:统计话术不通过的案例里,有多少同时 A2=失败。若占大头,说明**优化重心应放在检索召回/相关率,而非生成端**。

**数据/口径修正(让指标可信)**:
3. **重导 `retrievedDocs`(Top100 召回)**,修好 A5 与重排损耗——当前 36.3% 不可信。
4. **让 Excel/jsonl 带上 `usability.level`**,恢复 B6 自评校准。
5. 原始知识偏长时,**调大 `--doc-chars`**(如 6000)重跑,排除 B2 被截断低估的可能。

**若要提真实质量**:
6. 检索端:提升 A2(问题相关率)是第一杠杆——召回更准、重排别把对的挤掉。
7. 生成端:针对 B3 致命矛盾,强化"话术必须锚定原文"的约束(项目已有一致性校验,可核查是否生效/是否该更严)。

## 5. 附:重跑命令

```bash
cd /d/code/cmos-kb-agent/universal-agent

# 评审(检索双指标 + 话术质量);--testset 按 query 补齐 gold(标题+原子)
python scripts/eval_kbagent.py judge \
    --responses <你的目录>/responses.jsonl \
    --testset 测试集2.xlsx \
    --llm-url http://<llm_server_IP>:8002/llm_397b_api \
    --out eval_run1 --workers 3 \
    --doc-chars 6000          # 正文长时调大,避免 B2 被低估

# 只重算报表(不再调 LLM)
python scripts/eval_kbagent.py report \
    --verdicts eval_run1/verdicts.jsonl --out eval_run1
```

**产出文件**:
- `eval_summary.json` —— 全部汇总指标
- `eval_details.xlsx` —— 逐案例明细(每篇 Top3 的 gold命中/问题相关/理由 + B1~B5 打分)
- `badcases.csv` —— 失败案例清单(按失败原因筛查用)
